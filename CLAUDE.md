# Project: Logic Auto Parts

Nuxt 3 storefront for a European car-parts e-commerce site (BMW/Mercedes/Audi/Porsche/Land Rover). Backed by a WordPress REST API on `qsz.zoy.temporary.site/website_11f3c7a8` (hardcoded as `WP_URL` in `composables/useVehicleData.js`).

Note: `nuxt.config.ts` / `cms.x-trekkers.com` GraphQL config and a few components (`Post.vue`, `ReviewsSec.vue`, `MontBlacSlider.vue`) are leftovers from a different, unrelated prior project (a trekking site) - not mounted anywhere, ignore them.

## WordPress snippets (`wp-snippets/`)

The WP backend runs custom PHP snippets managed through a code-snippets plugin - **not files on the live server's disk**. This folder holds mirrored copies so changes can be developed/reviewed here.

**Workflow**: when a snippet needs a code change, edit the file in `wp-snippets/` here. The user then manually copies the updated code into the live WP snippet editor themselves - there is no direct write access to the live backend's PHP from this repo/session.

Nine snippets:
1. **`bulk-import-endpoint.php`** - CSV bulk import (`custom/v1/import-products`, `import-fitment`) plus the admin panel's product CRUD API: `custom/v1/admin-products` (list), `admin-product-save` (create/update), `admin-product-delete`. Auth: `X-Import-Secret` header (shared secret, constant `BULK_IMPORT_SECRET`), checked via `hash_equals`. This constant is reused by `orders-endpoint.php` below - **must stay active** alongside it. **Added 2026-08-07, live, pasted into WP**: `custom/v1/localize-product-images` (POST) - client asked (re: a planned ~500-product import) whether product images should be hotlinked live from the source (e.g. PA) or downloaded and hosted on our own server, and what the performance tradeoff would be; answered that we don't want the storefront depending on a third-party server, and built this. `bulk_import_products()`/`admin_save_product()` still store whatever image URL is given as-is (unchanged, stays fast regardless of import size). This new endpoint separately batch-processes `wp_custom_product_images` rows whose `picture_url` isn't already on our own uploads path: downloads each one (`download_url`/`wp_handle_sideload`), compresses it via `admin_compress_image_to_limit()` (reused from `admin-upload-image.php` - **must stay active** alongside this snippet too, though it's a soft dependency: localizing still works without it, just skips the 500KB compression pass), registers it as a real media library attachment, and rewrites `picture_url` to the new local URL. Deliberately capped at a small batch per call (`?limit=`, default 20, max 50) rather than doing it all in one request, since a 500-product import could mean 1000+ images and downloading them all synchronously would exceed PHP's execution time limit on shared hosting - `pages/admin/import.vue` has a new "Download & Host Images" button (step 3) that calls this endpoint in a loop, polling until `remaining` hits 0, and shows any per-image failures (left as the original external link on failure, not lost). Safe to re-run anytime, including after adding more products later.

**Bug found and fixed same day, before first live test**: initial version called `wp_handle_sideload(array(...), array(...))` with array literals - WordPress declares that function's first parameter by-reference, and PHP can't pass a literal by reference, so every call 500'd with "Argument #1 ($file) could not be passed by reference" (confirmed via curl against the live endpoint). Fixed by assigning to `$file_array`/`$overrides` variables first, then passing those. **Verified live via curl 2026-08-07** after the fix was pasted in: imported a 1-row test product with an external image URL, ran the endpoint twice - it correctly downloaded and re-hosted 4 pre-existing external images left over from earlier eBay-import testing (their URLs now point at this site's own `/wp-content/uploads/...`), and correctly left a deliberately-hostile test URL (a Wikipedia image) untouched with a clear per-image error ("Bad Request" - Wikimedia rejects WordPress's default outbound request signature, a source-specific quirk, not a bug here) rather than losing that image or failing the whole batch. Test product deleted after verification.
2. **`temporary-csv-fitment-parser.php`** - public/unauthenticated read routes: `custom/v2/vehicle` (drives all cascading vehicle dropdowns + the products sidebar tree) and `custom/v1/get-user-billing` (looks up a WP user by email - **no auth check, known PII exposure**, not yet fixed).
3. **`extract-ebay-fitment-data.php`** - one-off admin-only maintenance script (not a REST route), triggered via `?run_fitment_sync=1` in wp-admin. Parses a big eBay CSV export to backfill `wp_custom_product_fitment`. Treat as a throwaway tool, not part of the standing API surface.
4. **`orders-endpoint.php`** (added 2026-07-25, live) - order tracking tables + admin/customer order APIs.
5. **`export-products.php`** (added 2026-07-25, **live, pasted into WP**) - `custom/v1/export-products` / `custom/v1/export-fitment` (both GET), download the current catalog as CSV in the exact same column format `import-products`/`import-fitment` expect (round-trippable). Built because the client (Andres) asked for a CSV export to model his CRM's export against. `pages/admin/import.vue` now has "Export Current Products"/"Export Current Fitment" buttons that fetch with the `X-Import-Secret` header and trigger a client-side blob download (plain `<a href>` can't carry that header, so it's not a direct link).
6. **`admin-upload-image.php`** (added 2026-07-25, **live, pasted into WP**) - `custom/v1/admin-upload-image` (POST, multipart file field `file`). Compresses every upload server-side to fit under 500KB (`ADMIN_IMAGE_MAX_BYTES`) before registering it as a real WP media library attachment - re-encodes to JPEG and steps quality down (82→30), then as a last resort shrinks dimensions 30% and retries once. Returns the final attachment's public URL. Reuses `BULK_IMPORT_SECRET` like `orders-endpoint.php` does - `bulk-import-endpoint.php` must stay active.
7. **`brand-search-endpoint.php`** (added 2026-07-31, **live, pasted into WP**) - `custom/v1/brand-list` (GET, distinct `brand` values from `wp_custom_products` with product counts) and `custom/v1/products-by-brand` (GET, paginated products for one manufacturer brand - same response shape as `products-filter`). Public/unauthenticated, like `custom/v2/vehicle`. Built as a standalone new endpoint rather than extending `products-filter` because that route's source was never pasted into this repo (see below) - deliberately doesn't touch or depend on it. Powers the new footer "Shop By Brand" links in `components/PageFooter.vue` and the brand-only browsing mode in `pages/products.vue` (`isBrandMode` - active when `?brand=X` is present without `?make=`, skips the vehicle sidebar tree and calls this endpoint instead of `products-filter`).
8. **`product-search-endpoint.php`** (added 2026-07-31, **live, pasted into WP same day**) - `custom/v1/product-search?q=&page=&per_page=&sort=`, public/unauthenticated. Searches `wp_custom_products` by `sku` / `manufacturer_part_number` / `interchange_part_number` / `other_part_number` / `title` (LIKE match), exact SKU/part-number matches ranked first, same response shape as `products-filter`/`products-by-brand`. Built standalone for the same reason as `brand-search-endpoint.php` (doesn't touch `products-filter`). Powers the real SKU/part-number search that replaced `PageNavbar.vue`'s old make-only search box, and the new `?q=` search-only mode in `pages/products.vue` (`isSearchMode`). **Verified live via curl 2026-07-31**: `?q=355040911` (exact SKU) and `?q=Disc Brake` (keyword) both returned correct results with the real `brand` column (Pagid/DFC), confirming this endpoint doesn't have the make-vs-brand bug that `products-filter` has.
9. **`nuxt-vehicle-attributes-endpoint.php`** (found + fixed 2026-07-31, **live, pasted into WP same day**) - filename deliberately kept matching the live WP snippet's own name (ID 33196, created 2026-06-13, the oldest custom snippet) rather than being renamed to something more descriptive like the other 8 files, specifically so this repo and the live Snippets admin never disagree on what this one is called. Its docblock says "Ultimate Single Year Fitment Engine with Category Facets" - neither name reflects what it does, which is why it went unmirrored/unnoticed this whole project despite being the source for two heavily-used routes: `custom/v1/products-filter?year=&make=&model=&submodel=&engine=&page=&category=&sort=` (the Year/Make/Model results grid on `pages/products.vue`) and `custom/v1/product-detail?id=...` (single product page). Found by asking the user to cross-check every snippet name in the live WP Snippets screen against this repo's `wp-snippets/` folder - it was the one unaccounted-for entry. **Bug found and fixed in this file**: `get_filtered_vehicles_products()` (the `products-filter` callback) never selected the product's real `brand` column and instead hardcoded the response's `brand` field to `ucfirst($make)` - the vehicle make being searched (e.g. "BMW"), not the product's actual manufacturer brand (e.g. "Pagid"). Confirmed live via curl before the fix: `products-filter?make=BMW` returned `"brand":"BMW"` for item `2624`, while that item's real brand column is `"Pagid"` (per `admin-products`, which reads the real column). This is why the storefront showed vehicle make instead of manufacturer brand on every vehicle-search result (footer brand links via `products-by-brand`, and the product detail page via `get_single_custom_product_detail()`, were both unaffected - they already read the real column correctly). **Fixed** by adding `p.brand` to the SELECT and returning `$row['brand']` (falling back to `'Premium OE'`, matching the convention used everywhere else) instead of `ucfirst($make)`. **Verified live via curl 2026-07-31 after the user pasted the fix into WP snippet ID 33196**: `products-filter?make=BMW` now returns item `2621`/`2622` as `"brand":"DFC"` and `2623`/`2624` as `"brand":"Pagid"` - correct real brands, no more hardcoded make.

`custom/v1/process-square-payment` was also external/unseen originally (confirmed live via wp-json discovery, and via the GBP/USD bug below) - but the user didn't have its source saved anywhere to hand over, so **`wp-snippets/process-square-payment.php` (added 2026-07-25) is a from-scratch replacement**, not a mirror of whatever was live before. **Live, pasted into WP** - it fully replaces the old route. Charges the card server-side via Square's Payments API (`wp_remote_post` to `/v2/payments`), hardcodes `currency: USD` (fixing the bug below), and calls `custom_record_order()` from `orders-endpoint.php` on success. **`SQUARE_ACCESS_TOKEN` is now filled in with a real Sandbox Access Token** (user pasted it in chat 2026-07-25) - treat this file as containing a live secret from here on, same caution as `BULK_IMPORT_SECRET`/the eBay API keys mentioned elsewhere in project memory. It's a *sandbox* token (lower stakes than production), but still shouldn't be pasted into future chats/commits beyond what's already here.

## Checkout flow bug found & fixed (2026-07-25)

`pages/checkout.vue`'s `WP_URL` constant was missing a trailing slash before its query string: `'https://qsz.zoy.temporary.site/website_11f3c7a8?rest_route=/'`. WordPress 301-redirects that to the trailing-slash form, and a cross-origin POST that hits a redirect gets blocked by the browser (`TypeError: Failed to fetch`) - so every real checkout attempt was silently dying before ever reaching `process-square-payment`, surfacing only as the generic toast "Failed communicating with core gateway." **Fixed** by adding the trailing slash (`.../website_11f3c7a8/?rest_route=/`). Confirmed via a live browser test (filled real guest details + a Square sandbox test card, patched `window.fetch` to inspect the actual request/response) that the request now reaches the backend - which is how Bug 2 above (GBP vs USD) surfaced next.

## Database tables in use

- **`wp_custom_products`** (PK `item_id`, **not** AUTO_INCREMENT - always compute `SELECT MAX(item_id)+1` before inserting) - one row per product: sku, title, price, description, brand, placement_on_vehicle, manufacturer_part_number, interchange_part_number, other_part_number, fitment_notes, vin_required_message.
- **`wp_custom_product_fitment`** (FK `product_id` → `item_id`) - one row per year/make/model/submodel/engine combo a product fits.
- **`wp_custom_product_images`** (FK `product_id` → `item_id`) - one row per product image (`picture_url`).
- **`w84_custom_app_users`** (id, username, email, password [WP-style bcrypt hash], created_at) - the site's **own custom login/register system**, separate from WordPress's core `wp_users` table. This is the real "customer account" table for the storefront (confirmed via live phpMyAdmin dump 2026-07-25, 3 rows). Note the `w84_` prefix differs from the `wp_custom_*` naming used elsewhere - a literal table name, not `$wpdb->prefix`-driven, so don't assume other tables share this prefix.
- **`wp_custom_orders`** / **`wp_custom_order_items`** (added 2026-07-25, schema in `orders-endpoint.php`, **not yet created on the live DB** - visit `?run_orders_setup=1` as admin once the snippet is pasted in) - see Orders section below.

Both fitment/images and order/order-items are one-to-many per product/order - never assume a flat 1-row shape.

## Stock status / availability (added 2026-07-31)

- **New column**: `wp_custom_products.stock_status` (`VARCHAR(20) NOT NULL DEFAULT 'in_stock'`). Added via a one-off migration in `bulk-import-endpoint.php` (same pattern as `orders-endpoint.php`'s `?run_orders_setup=1`) - visit any wp-admin page with **`?run_stock_status_setup=1`** once the updated snippet is pasted in. - **`admin_save_product()`** (`bulk-import-endpoint.php`) now accepts `stock_status` from the admin form; anything other than the literal string `'out_of_stock'` is coerced to `'in_stock'`.
- **`admin_list_products()`** (`bulk-import-endpoint.php`) now also selects `stock_status`, shown as a badge column in `pages/admin/products/index.vue`.
- **Read endpoints updated to select + return `stock_status`**: `nuxt-vehicle-attributes-endpoint.php` (both `products-filter` and `product-detail`), `brand-search-endpoint.php` (`products-by-brand`), `product-search-endpoint.php`. All of them were touched since a product can surface through any of these three search paths.
- **`components/AdminProductForm.vue`**: new "Availability" dropdown (In Stock / Out of Stock) next to Brand, defaults to `in_stock` for new products and reads `initial.stock_status` for edits.
- **Frontend badges**: `pages/products.vue` (product card) and `pages/product/[id].vue` (detail page, badge didn't exist there before) now render "In Stock / Ready To Ship" (emerald) or "Out Of Stock" (gray) based on `product.stock_status`, instead of the old hardcoded text.
- **Not yet pasted into WP**: `bulk-import-endpoint.php` (updated), `nuxt-vehicle-attributes-endpoint.php` (updated), `brand-search-endpoint.php` (updated), `product-search-endpoint.php` (updated). **User must run `?run_stock_status_setup=1` after pasting the updated `bulk-import-endpoint.php`**, otherwise the other three updated snippets (which now `SELECT p.stock_status`) will hard-error with "Unknown column" until the column exists.
